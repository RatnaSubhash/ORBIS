 ORBIS
 Master Project Specification
An Intelligent Context-Aware Desktop Agent for Workspace Continuity and Autonomous Computer Assistance
Target: Windows 11 desktop | UI: Electron + React | Gateway: FastAPI | Memory: SQLite + FAISS + Workspace Knowledge
Graph
This document is the functional blueprint for what ORBIS should do, how users should command it, how tasks should execute,
how continuity should work, how restoration should work, what the interface should show, and what ORBIS must never do.
1. Product Definition
ORBIS is a general-purpose, local-first desktop AI agent. A user should be able to speak or type a natural-language request and
ORBIS should determine whether the request needs an answer, research, file access, coding, terminal execution, document
generation, system control, workspace retrieval, restoration, or a multi-step combination of these capabilities.
The central research differentiator is workspace continuity. ORBIS should reconstruct task-level context across applications, files,
browser resources, events, sessions, intent, and relationships so that a user can return later and continue meaningful work
instead of starting from zero.
General-purpose does not mean unrestricted. ORBIS can perform an authorized digital task only when an implemented and
safety-controlled capability exists.
2. Core User Experience
  User gives a request.
  ORBIS resolves conversational references and current context.
  ORBIS determines the intent and whether fresh information is required.
  ORBIS grounds the request using current workspace and authorized historical context.
  ORBIS creates a plan for multi-step work.
  Safety policy validates the plan.
  Approval is requested for actions requiring it.
  Registered tools execute the plan.
  Live events are streamed to the UI.
  Postconditions are verified.
  Relevant results are recorded for continuity.
  ORBIS explains what happened, what could not be done, and what can happen next.
 
3. What ORBIS Should Do
  Answer normal questions.
  Explain technical concepts at beginner or technical depth.
  Research current information and provide sources.
  Compare sources and identify disagreements.
  Inspect approved files and folders.
  Create supported documents and project artifacts.
  Read and summarize project files.
  Run controlled terminal commands.
  Assist with coding and debugging.
  Observe authorized workspace activity.
  Segment activity into meaningful work sessions.

4. What ORBIS Must Not Do
  No keylogging.
  No password harvesting.
  No credential scraping.
  No unrestricted surveillance.
  No hidden microphone recording.
  No unrestricted clipboard capture.
  No arbitrary bypass of OS security.
  No fake execution results.
  No fake research sources.
  No silent high-risk actions.
  No direct unrestricted tool-execution API.
  No claim of perfect restoration.
  No claim of certainty when continuity evidence is weak.

8. Natural-Language Semantics
  'latest' means fresh retrieval when current information matters.
  'yesterday' means the user's local date and the stored session timeline.
  'that' refers to the most recent unambiguous artifact or topic.
  'continue' means identify the most relevant unfinished work before acting.
  'do it' refers to the current pending plan only if the reference is unambiguous.
  If multiple files/resources match, ask instead of guessing.
  If the user changes topic, preserve useful artifacts but change active task focus.
  'stop' or 'cancel' should terminate pending execution as safely as possible.
 
9. Conversation Context
ORBIS must maintain bounded multi-turn context. It should track recent turns, resolved references, current task, current artifacts,
selected resources, and active view. It should not retain an unlimited conversation history as the sole memory mechanism.

10. Workspace Observation
Observation is passive and privacy-conscious. It provides evidence for continuity rather than acting as surveillance.
  Observe supported active application/window state.
  Observe approved file/workspace events.
  Store timestamps and task-related metadata.
  Apply protected path and privacy exclusions.
  Do not capture passwords.
  Do not keylog.
  Do not persist raw audio.
  Do not capture unrestricted screenshots.
  Do not expose protected filenames through directory listing.
 
11. Sessionization
Raw events must be grouped into coherent work sessions. Sessionization should consider time, active application continuity,
project/resource relationships, event sequences, and task signals.
A session is a meaningful unit of work, such as developing ORBIS, researching a topic, preparing a report, or debugging a build. It
is not simply an arbitrary time interval.

13. Knowledge Graph

14. Semantic Memory and Hybrid Retrieval
Semantic embeddings and FAISS provide similarity retrieval. ORBIS should combine semantic similarity with lexical overlap,
recency, project relevance, application continuity, and graph proximity.
A semantically similar old session must not automatically outrank a recent, project-matching session. Retrieval should expose
evidence and confidence.
15. Intent Continuity Engine
ICE should answer three questions: what was the user trying to accomplish, whether the work appears complete, and what action
could logically continue it.
  Use recent workspace events.
  Use prior task language.
  Use file/resource state.
  Use application continuity.
  Use temporal gaps.
  Use completion evidence.
  Do not convert weak evidence into certainty.
  Explain uncertainty when appropriate.

17. Safety Model
Deterministic safety rules are authoritative. The LLM cannot override them.
18. Approval
  Show exactly what ORBIS plans to do.
  Show the target resource.
  Explain why approval is required.
  Show reversibility when known.
  Provide Approve, Reject and Cancel.
  Never execute a high-risk step while approval is pending.
 
19. Task State Machine
Canonical lifecycle:
IDLE → REQUEST_RECEIVED → NORMALIZING → CONTEXT_GROUNDING → INTENT_CLASSIFIED → PLAN_CREATED
→ SAFETY_CHECK → APPROVAL_REQUIRED/EXECUTING → STEP_STARTED → TOOL_EXECUTION → VERIFICATION
→ STEP_COMPLETED → next step → TASK_COMPLETED. Failures may transition to REPLAN or TASK_FAILED; rejection
transitions to TASK_CANCELLED.
20. Verification Rules
A successful process exit code is not automatically proof that the user's intended outcome occurred.
21. Web Research
  Search only when needed.
  Use bounded search/fetch.
  Validate URLs and redirects against SSRF policy.
  Treat external pages as untrusted input.
  Never obey instructions embedded in external pages as ORBIS policy.
  Preserve evidence/source attribution.
  Distinguish snippets from fetched content.
  Do not claim current information without current retrieval.

  Cancel must be safe.
  Voice should surface final results, not hidden reasoning.

33. Extensibility Rule
Every new capability should be introduced as a controlled tool with a schema, risk classification, validation, execution method,
verification method, tests, and UI exposure. If the capability does not exist, ORBIS must say so rather than simulating it.
  Future email/calendar integrations require explicit authorization.
  Browser automation requires its own safety model.
  Office formats require supported libraries and verification.
  Repository actions require explicit scope and approval.
  New OS controls require dedicated testing.
  External integrations require license and security review.

35. Final Product Definition
ORBIS should be experienced as one coherent assistant, not a chatbot plus unrelated utilities. The agent should understand a
request, connect it to the user's current or historical workspace, decide what tools are required, safely execute authorized steps,
verify the outcome, explain the result, and preserve enough context that the next interaction can begin from where the previous
work ended.
The most important loop is: WORK → OBSERVE → UNDERSTAND → REMEMBER → RETURN → RECONSTRUCT →
RESTORE → CONTINUE.
The project is successful when ORBIS can demonstrate that loop truthfully with real workspace data, real task execution, real
safety boundaries, and real verification.
